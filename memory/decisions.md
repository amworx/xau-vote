## D-20261005-004 - Sentiment-layer scoring: narrow band wins, and macro alignment is coverage-gated

- **date:** 2026-10-05
- **context:** first vertical slice of A85.1 - `sentiment-layers` Edge Function writing `sentiment_layers` from US Treasury real yields (market_implied, 20) and CFTC managed money (positioning, 25). Policy (35) and WGC (20) are written as explicit null rows, not omitted.
- **decision 1 - A85.3 bands overlap, and the narrower band wins.** The methodology lists `0 if percentile 20-60` and `-1 if percentile 20-40`, so a reading of 32.6 satisfies both. Silently picking either changes a live verdict, so the ambiguity is resolved in favour of the NARROWER, more informative band: `<20 and 20-40 -> -1`, `40-60 -> 0`, `60-80 -> +1`, `>80 -> +1`.
- **decision 2 - the A85.3 +/-2 extremes stay unreachable until price is read.** A85.3 attaches +/-2 to a price-trend leg and separately flags POSITIONING_DIVERGENCE. The function does not read price, so `cotScore(percentile)` never returns +/-2 and the row records `trend_confirmed: false` and `positioning_divergence: null`. Scoring +/-2 off positioning alone would invent a confirmation that did not happen.
- **decision 3 - macro alignment is coverage-gated at 50%, sentiment is not.** `confluence.dart` L13 reads ONLY `macro.alignment` and `sentiment.alignment`; the individual impulses are stored but unused, and `macro < 0` calls `veto(v6DirectionConflict)`. Positioning is one COMPLETE A85.1 layer, so its alignment passes straight through - and a negative there only applies a confidence penalty, which is what A86 requires of a weekly reading. Macro alignment stays NULL until >=50% of macro-side weight (75) is measured; today only market_implied is, so coverage is 20/75 = 27% and alignment stays null. Letting a 27% sample veto a setup would be inventing conviction in either direction. The measured impulse is still surfaced in `MacroState.realYieldImpulse` and in `macroCoverage`, so the data is visible while it is not yet strong enough to act on.
- **consequence:** the Treasury reading is live and displayed but deliberately cannot move a verdict yet; COT can contribute confidence. When the policy layer lands, coverage reaches 55/75 = 73% and macro alignment resolves with no code change beyond the ingest.
- **null vs zero (unchanged, re-affirmed):** an unmeasured layer is `null`, never `0`. `0` means neutral; silence is not neutrality. The 1970 epoch the writer uses for "never measured" is mapped back to `null` in Dart so no caller can render it as a real date.
- **status:** accepted

## D-20261005-005 - CFTC is read through its Socrata API, not www.cftc.gov

- **date:** 2026-10-05
- **finding:** `www.cftc.gov` serves the weekly `.txt` and yearly `.zip` files behind a bot challenge. From Supabase egress both return HTTP 403 with a Cloudflare "Just a moment" interstitial, and a spoofed browser User-Agent does NOT clear it (probed: 403 with and without UA). The first deployed run therefore wrote `market_implied` and reported `positioning unavailable` - it degraded honestly rather than scoring COT as 0.
- **decision:** read `publicreporting.cftc.gov` (CFTC's own Socrata API) instead. Verified 200 from the same egress. Dataset `72hh-3qpy` "Disaggregated - Futures Only". Rejected: `kh3c-gbw2` "Combined" (folds options in, which A81.6 does not ask for) and `ubmb-6exi` (frozen since 2022-07-28, missing the managed-money columns).
- **why it is also better, not just reachable:** one ~0.7s query instead of ~6.5MB of yearly archives; the FULL 156-week window A81.6 asks for (three calendar years of zips yielded only 144 weeks, because the running year is always partial); and columns selected by name so a CFTC schema change cannot silently shift a value into the wrong field.
- **cross-check:** the Socrata row for 2026-09-29 (open interest 406456, managed money 131711 / 11393, net 120318) matches the weekly `.txt` byte for byte.
- **latency note:** `home.treasury.gov` costs ~18s per request from Supabase egress regardless of size (a 6.8KB CSV took 18.3s). The function therefore fetches only the current year and requests the prior year only when the current one has fewer than six usable 10Y observations. FRED carries the same series (DFII5/DFII10) but did not respond at all when tried, so it is not a usable fallback.
- **consequence:** run time 40s -> ~23s. pg_net's response timeout is still shorter than that, so a scheduled run leaves a NULL status in `net._http_response` even though the function completes and writes correctly. Raising `net.http_timeout` requires a role the SQL API does not have, so this is an owner-level follow-up. The data path itself was verified twice through `xv_invoke_function`.
- **status:** accepted

## D-20261005-006 - xv_invoke_function's allowlist is a real gate

- **date:** 2026-10-05
- **finding:** `cron.schedule('xv-sentiment-layers', '21 21 * * *', ...)` succeeded and the job appeared healthy in `cron.job`, but `public.xv_invoke_function` validates its argument against a hardcoded allowlist that did not contain `sentiment-layers`. Every nightly run would have raised, while `cron.job.active` still reported true - the exact failure mode where a silent data freeze looks like a healthy schedule.
- **decision:** add `sentiment-layers` to the allowlist (migration 0005) and verify by calling `xv_invoke_function('sentiment-layers')` and watching the rows change.
- **secondary fix:** `sentiment_layers.updated_at` had a column default but no trigger, so it never moved on update and could not distinguish a fresh write from a frozen value. Added the trigger (migration 0006). This was found only because the first verification attempt tried to use `updated_at` as the change signal and appeared to fail.
- **general lesson:** after adding a scheduled function, always confirm the dispatcher can name it, and always have a timestamp column that actually moves on write before using it to verify anything.
- **status:** accepted

## D-20261005-007 - The macro/sentiment overlay must be side-aware (correctness bug)

- **date:** 2026-10-05
- **severity:** high - would have silently destroyed the short side as soon as real macro data was wired in.
- **finding:** `confluence.dart` step 13 read `macro.alignment` and `sentiment.alignment` WITHOUT reference to the traded direction. Every other check in the scorer is side-aware (`bull ? ... : ...`), so this was an outlier, not a design choice. Consequences: `macro < 0` called `veto(v6DirectionConflict)` on longs AND shorts, so a bearish macro would have vetoed the exact trade it favours; and a bullish macro credited longs while giving shorts no penalty at all, so the short side was systematically unrewarded and over-penalised.
- **why it went unnoticed:** nothing ever fed `ConfluenceInput.macro` / `.sentiment`, so both were always null and the block was dead code. Wiring real data in is what made the bug reachable.
- **decision:** each alignment is flipped for shorts before use, so what reaches the score and the veto is "does this layer agree with the trade being evaluated". `macroAgrees` / `sentimentAgrees` are exposed on `ConfluenceResult` alongside the raw `macroAlignment` / `sentimentAlignment`, because a UI must be able to say "macro: bearish" on a short rather than flipping the label to match the trade.
- **unchanged:** macro opposing still vetoes (Rule 3); sentiment opposing still only costs confidence and never vetoes (§6).
- **coverage added:** seven tests, including two that would have failed before the fix (bearish macro supports a short; bullish macro actively penalises a short).
- **status:** accepted

## D-20261005-010 - Ask for the install permission instead of naming it

- **date:** 2026-10-05
- **reported symptom:** the in-app updater could not install the new version; it looked like a missing permission.
- **root cause (three defects, one invisible):**
  1. `MainActivity.kt` answered `canInstallPackages` with `SDK_INT >= O`. That is true on every device this app can run on, so Dart always believed installation was permitted. `REQUEST_INSTALL_PACKAGES` is NOT granted at install time - from Android 8 the user grants it per-source in Settings - and `checkSelfPermission` keeps returning GRANTED regardless. The only truthful question is `PackageManager.canRequestPackageInstalls()`.
  2. There was no handler that opened the permission screen at all. The app could detect nothing and ask for nothing, so the user had to find the setting unaided.
  3. `installApk` called `startActivity` then `result.success(null)` unconditionally. The system actually refuses inside the installer UI, so Dart was told the launch worked while nothing happened - the button looked dead.
- **decision:**
  - `canInstallPackages` now calls `packageManager.canRequestPackageInstalls()`, true unconditionally below Android 8.
  - New `requestInstallPermission` handler opens `Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES` scoped to `package:$packageName`, falling back to the app-details page, and short-circuits when already granted.
  - `installApk` checks the grant BEFORE launching and reports `needs_permission` as a distinct error code; a null result from the capability check is treated as "unknown", not "denied", so nothing is blocked by a missing capability.
  - The install intent gained `ClipData` (the read grant on the data URI alone is not honoured by the package installer on several Android versions) plus `EXTRA_NOT_UNKNOWN_SOURCE` and `EXTRA_INSTALLER_PACKAGE_NAME`.
  - `installApk` returns `InstallResult`/`InstallOutcome` instead of `bool`, so "needs permission" survives to the UI. The old `bool` collapsed every failure into the same unfixable message.
- **UI:** the INSTALL action now offers an `ALLOW` action that opens the system screen. This is a functional snackbar action reusing the existing visual language, NOT a new designed surface - a proper first-class permission explainer is still available and would go through the browser-prototype-then-approval route first.
- **verification:** 12 new tests across the MethodChannel contract (granted / not granted / cannot-tell, and each error code mapping). The Kotlin compile caught a wrong constant - `ACTION_MANAGE_INSTALL_PERMISSIONS` does not exist; it is `ACTION_MANAGE_UNKNOWN_APP_SOURCES`. Built APK verified with aapt2: `1.0.8`/code 9, `REQUEST_INSTALL_PACKAGES` present.
- **status:** accepted

## D-20261005-013 - The analysis card must distinguish "failed" from "not run yet"

- **date:** 2026-10-06
- **found on hardware:** the Radar card read "No analysis yet - waiting for enough history to evaluate the 1H regime" while `market_bars` held 342 closed 1h bars, 597 closed 15m, 423 closed 30m and 1292 closed 5m with ZERO gaps. The copy was confidently wrong.
- **two causes, both real defects:**
  1. `AnalysisService.startPolling` used `Timer.periodic` only, so the first scan did not run for a full 60 seconds after launch. `LiveData.startPolling` fires immediately; the analysis service did not. A one-minute delay is indistinguishable from missing data.
  2. `refresh()` catches everything into `_error` and returns null, but the card only checked `scan == null` and never rendered `error`. A permanently throwing scan therefore displayed a reassuring "waiting for history" message indefinitely.
- **decision:** `startPolling` runs one scan immediately; `AnalysisVerdictCard` takes `error` and renders an "Analysis failed" state in red with the message and a RESCAN action, while "no analysis yet" is reserved for a scan that genuinely has not produced a result.
- **general rule this restates:** a message that asserts a cause must not be shown when the cause is unknown. "Waiting for enough history" is a claim about the database, and it was false.
- **status:** accepted

## D-20261006-002 - Independence must be counted in SOURCES (critical correctness bug)

- **date:** 2026-10-06
- **severity:** critical. The app was presenting fabricated trade setups as multi-source consensus, with a COPY LEVELS button.
- **what was happening:** `collect-ideas` runs every 15 minutes and seeds HARD-CODED fixture ideas with templated reasoning ("Bounce off the shelf; momentum turning up."), all under `source_id = manual-seed` (`url = internal://manual-seed`), attributed to three fake authors `desk-a` / `desk-b` / `desk-c`. 636 such ideas existed.
- **the bug:** `build-consensus` compared `camp.length` against `MIN_INDEPENDENT_SOURCES`. `camp.length` is the count of DISTINCT FINGERPRINTS, not publishers. The fingerprint includes `author`, so one source labelling its rows desk-a/b/c defeats the check entirely - exactly the divided-room case spec §5 says to collapse. Live evidence before the fix: a `DEVELOPING` LONG, strength 86-87, with real entry/stop/TP, built from 9-11 ideas whose `distinct_sources` was **1**.
- **fix (three parts):**
  1. The guard now counts DISTINCT `source_id` in the dominant camp, and compares that to `MIN_INDEPENDENT_SOURCES`.
  2. Sources whose `url` begins `internal://` are excluded from the independence count entirely, so pipeline seed data can never stand in for an external publisher (D-20261005-001: "1-of-1 is not consensus").
  3. The score's independence component (`indepW`) was also `camp.length / 4`; it now uses distinct external sources, so one publisher posting nine variants cannot score full marks on independence.
- **verified live after deploy:** `NO_CONSENSUS / SINGLE_SOURCE` with `{ideas:10, distinct_sources:1, distinct_external_sources:0, internal_seed_sources:1}`. The single open DEVELOPING setup was expired; the phone now shows NO CONSENSUS with no levels and no COPY LEVELS button.
- **the response now reports the independence breakdown** so "0 of 0 sources" is legible as a refusal rather than an absence.
- **status:** accepted

## D-20261006-006 - Two corrections to my own claims, after a fourth expert review

- **date:** 2026-10-06
- **status:** accepted
- **CORRECTION 1 - "Unproven" is not "disproven".** I wrote that the consensus premise is "structurally dead" and "dead-ended". That overclaims. The evidence supports: **publisher consensus is unavailable at zero cost under current licensing terms.** It does not support a claim about whether publisher consensus would have had any value. The distinction matters because a false-negative is a far more expensive error here than a false-positive - it would cause us to abandon something that works. Recorded language change: unproven, not disproven.
- **CORRECTION 2 - provenance is NOT economic independence. This limits my own fix.**
  D-20261006-002 made independence count DISTINCT `source_id` and excluded `internal://` sources. That is correct and it did stop the `desk-a/b/c` failure. But it proves **identity** separation, not **economic** independence. One entity operating two branded publishers produces two valid distinct source IDs and passes the gate perfectly.
  - What provenance machinery actually proves: origin, and tamper evidence (signed manifests, allowlists, hash chains, append-only storage).
  - What it cannot prove: that two publishers are not the same desk, the same data vendor, the same algorithm, or the same incentive.
  - Genuine economic independence is an organisational question requiring ownership disclosure, conflict-of-interest declarations, source attestation and periodic audit - not a technical control.
  - **Every expert proposed provenance as the answer to the independence problem. Provenance is not the answer to that question.** Recorded so D-20261006-002 is not read as having solved independence.
- **CORRECTION 3 - the same trap applies to our own validation.** Overlapping 15M setups inside one gold move are economically ONE observation, not N. Counting them as independent would manufacture statistical confidence out of autocorrelation - the identical error class as counting nine seed rows as nine publishers, applied to our own backtest. Signals must be clustered before any sample size is quoted. This reconciles Expert 2's "n of 200-300 independent trades" with Expert 4's "the required sample depends on frequency, asset class, risk model and effect size".
- **carried forward as the strongest guidance:** define the validation protocol BEFORE testing (freeze scoring logic and parameter versions; separate development, validation and untouched out-of-sample; walk-forward rather than one optimised backtest; record spread, slippage, latency, fees and rejected orders; report sample size, expectancy, drawdown, confidence intervals and regime-specific results), and **publish failed tests as well as successful ones.**
- **commercial test adopted:** can a credible partner pay for the engine BEFORE substantial additional engineering? If not, do not build licensing infrastructure.
- **status:** accepted

## D-20261006-007 - Validation metric: expectancy in R, not win rate (sample-efficiency finding)

- **date:** 2026-10-06
- **finding from expert review, checked arithmetically.** An expert specified win-rate sample sizes of "~380 trades for 55% vs 50%" and "~2400 for 52% vs 50%". Both are optimistic by roughly 4x. Two-proportion test, alpha 0.05 two-sided, power 80%:
  - 55% vs 50% -> **1,563 per group**
  - 52% vs 50% -> **9,795 per group**
- **consequence:** detecting a 2-percentage-point win-rate edge is almost certainly out of reach for a selective 15M system on any tolerable timeline. At even 4 signals/day it is ~6.5 years for the 52% case.
- **the better metric is expectancy in R-multiples**, because R has far lower variance than a binary win/loss outcome. To detect a mean R of +0.15 at 95% confidence: sigma_R 1.0 -> **171 trades**; sigma_R 1.5 -> **384 trades**.
- **so the two approaches differ by 4x to 25x in sample efficiency.** Expert 2's "n of 200-300 independent trades" was correct for expectancy; Expert 5's figures were for win rate and are the wrong metric to plan around.
- **decision:** the pre-registered protocol scores **expectancy in R, net of measured spread**, with win rate reported only as a secondary descriptive. Primary metric fixed BEFORE any testing so the holdout is not spent choosing a metric after seeing results.
- **unchanged and still required:** cluster overlapping setups within one gold move into a single observation before quoting any sample size (D-20261006-006); prospective spread collection, because historical spread aggregates are not this venue's cost.
- **unverified claim flagged:** "historical spread underestimates cost by 20-60%" is plausible and directionally right but I have not verified the magnitude. Treat as a hypothesis to measure, not a planning constant.
- **status:** accepted
